OAuth 2.0: 비밀번호 대신 필요한 권한만 허용하기(Test)

2026년 9월 23일4m

OAuth 2.0은 앱이 다른 서비스의 데이터에 정해진 범위로 접근하도록 권한을 부여하는 표준입니다. 일정 정리 앱이 내 캘린더를 읽는 경우로 살펴보겠습니다. 이 흐름에서 사용자는 캘린더 계정의 비밀번호를 일정 정리 앱에 넘기지 않습니다.

등장하는 역할은 네 가지입니다. 사용자는 캘린더 주인, 클라이언트는 일정 정리 앱입니다. 인가 서버는 사용자와 접근 허용 여부를 확인하고 토큰을 발급합니다. 리소스 서버는 캘린더 데이터를 제공하는 API입니다. 두 서버는 같은 서비스 안에 있어도 역할이 다릅니다.

① 필요한 권한을 요청합니다

앱에서 ‘캘린더 연결’을 누르면 브라우저가 인가 서버로 이동합니다. 앱은 ‘캘린더 읽기’에 필요한 권한 범위인 scope를 요청합니다. 인가 서버는 사용자를 확인하고 접근 허용 여부를 결정합니다. 로그인이나 동의 화면은 필요한 경우에 표시됩니다.

② 인가 코드를 액세스 토큰으로 교환합니다

접근이 허용되면 인가 서버는 브라우저를 앱으로 돌려보내며 짧게 유효한 일회용 인가 코드를 전달합니다. 앱은 이 코드를 인가 서버의 토큰 엔드포인트에 보내 액세스 토큰을 요청합니다. 서버가 요청을 검증한 뒤 토큰을 발급합니다. 코드는 토큰 교환에 쓰는 값이며, 캘린더 API를 호출하는 토큰과는 다릅니다.

PKCE에서는 앱이 요청마다 만든 무작위 verifier를 보관하고, S256 방식으로 계산한 challenge를 인가 요청에 보냅니다. 토큰 교환 시 인가 서버가 앱이 보낸 verifier로 challenge를 다시 계산해 처음 값과 대조하므로, 코드만 훔친 공격자의 교환 요청을 막습니다.

③ 토큰으로 허용된 데이터에 접근합니다

앱은 액세스 토큰을 제시해 캘린더 API를 호출합니다. API는 토큰의 유효성과 권한을 검증한 뒤 허용된 데이터를 제공합니다. 토큰이 만료되었거나 필요한 권한이 없으면 해당 요청을 거절합니다. 읽기만 필요한 앱이라면 수정·삭제 권한까지 요청할 이유가 없습니다.

인증은 ‘누구인지 확인’, 인가는 ‘무엇을 허용할지 결정’입니다. OAuth 2.0의 핵심은 인가입니다. 앱이 사용자 로그인과 신원을 확인하는 데는 OAuth 2.0 위에 인증 기능을 더한 OpenID Connect(OIDC)를 함께 사용할 수 있습니다. OIDC의 ID 토큰과 API 접근용 액세스 토큰도 용도가 다릅니다.

공식 문서: OAuth 2.0 · RFC 6749 · PKCE · RFC 7636 · 보안 권고 · RFC 9700 · OpenID Connect Core

방문 통계
같은 브라우저의 방문을 한국 시간 기준 하루 한 번 집계합니다. 무작위 식별자를 브라우저에 저장하고 서버에는 해시한 중복 확인값을 보관합니다. 지난 날짜의 확인값은 자정 이후 정리하며, 집계 수치는 유지합니다. IP 주소와 방문 페이지는 집계 저장소에 보관하지 않습니다.

사이트 보안과 외부 서비스
과도한 요청을 제한하기 위해 IP 주소를 사용합니다. Cloudflare·GitHub도 사이트 제공과 보안을 위해 접속 정보를 처리할 수 있으며, Turnstile은 IP·브라우저 정보를 봇 차단과 탐지 기능 개선에 이용합니다. 외부 서비스에서 정보가 국외 처리될 수 있고, 보관에는 각 업체의 정책이 적용됩니다.
Cloudflare Turnstile · Cloudflare · GitHub

브라우저 저장정보
방문 식별자는 다른 날짜에 재방문하면 교체하고, 화면 모드 설정은 브라우저에 유지합니다. 브라우저의 ‘쿠키 및 사이트 데이터’ 설정에서 삭제하거나 저장을 제한할 수 있습니다. 제한하면 방문 집계와 화면 설정 저장이 작동하지 않을 수 있습니다.
