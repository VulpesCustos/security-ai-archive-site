1. 상용 AI에 자료를 넣기 전: 마스킹보다 먼저 줄일 정보가 있습니다

직원이 고객 이메일의 문장을 다듬고 싶을 뿐이라면 고객 실명, 계약번호, 전체 메일 이력까지 제공할 필요는 없습니다. 업무에 필요한 부분만 추리고, 식별정보를 바꾸며, 남은 맥락으로 비밀이 드러나지 않는지 확인하는 순서가 좋습니다.

다음은 예시입니다.

표는 좌우로 움직여 볼 수 있습니다.

방법 변경 예시 남는 위험과 사용 요령
별표 가림 김테스트 → 김*** 조직·직책·사건 날짜가 남으면 특정인을 짐작할 수 있음. 이름만 가렸다고 충분하지 않음
일관된 치환 김테스트, 가상거래처 해솔 → 고객 A, 거래처 B 문맥을 유지하기 좋음. 원래 값과의 대응표는 AI에 보내지 않고 별도 보호
범주화·일반화 정확한 생년월일 → 연령대, 상세 주소 → 지역 수준 작은 조직이나 드문 사건에서는 조합만으로도 식별될 수 있음
더미(가상) 데이터 실제 주문을 가짜 주문번호·날짜·금액으로 대체 코드 구조·서식 검토에 유용. 실제 분석·정산 결과를 얻는 용도로 혼동하지 않기
불필요한 내용 제거 메일 본문에서 서명·연락처·이전 대화 삭제 질문에 꼭 필요한 내용만 남김. 첨부파일과 문서 메타데이터도 별도로 확인

예를 들어 입력을 이렇게 바꿔볼 수 있습니다.

원래 요청의 예시: “김테스트 고객의 7억 3천만 원 계약과 미공개 제품 출시 일정이 담긴 이 메일을 부드럽게 고쳐줘.”

업무에 맞게 줄인 요청: “거래처에 일정 변경을 정중하게 안내하는 메일 초안을 작성해줘. 고객명·계약금액·제품명·날짜는 [고객명], [금액], [제품명], [날짜] 자리표시자로 남겨줘.”

이 경우에는 실제 계약정보를 AI에 넘길 이유가 거의 없습니다. 초안을 받은 뒤 승인된 업무 환경에서 값을 채우면 됩니다. 반대로 실제 수치 분석이 필요한 업무라면 데이터를 임의로 바꾸기보다, 그 데이터를 처리하도록 승인된 환경을 사용해야 합니다.

마스킹은 자동으로 익명화를 의미하지 않습니다. 가명정보도 개인정보이며, 재식별 가능성과 법적 처리 요건을 검토해야 합니다. 사람 이름을 모두 지워도 미공개 가격·제품 계획·내부 취약점은 여전히 기업의 비밀정보입니다. 개인정보보호위원회 가명정보 처리 가이드라인, 2026년 3월 개정

PDF의 검은 사각형 아래 원문이 남아 있거나, 문서 주석·변경 이력·숨긴 시트·파일명에 정보가 남는 경우도 점검해야 합니다. 가린 모양을 보는 것과 실제 추출되는 내용을 확인하는 것은 다릅니다. 마스킹된 산출물을 다시 열어 복사·텍스트 추출·첨부 확인을 수행하고, AI가 만든 결과를 외부로 보낼 때도 사람이 검토합니다.

2. ChatGPT와 Claude: 네 가지 설정을 따로 확인합니다

제품명이 같아도 개인용, 기업용, API의 조건은 다릅니다. 메뉴는 요금제·플랫폼·조직 정책에 따라 달라질 수 있습니다.

표는 좌우로 움직여 볼 수 있습니다.

확인할 것 의미 흔한 오해
학습 사용 입력·출력이 모델 개선에 사용되는가? 학습을 끄면 저장도 하지 않을 것이라는 생각
보관·삭제 대화·파일·로그가 어디에 얼마나 남는가? 대화 삭제가 모든 복사본의 즉시 삭제라는 생각
기억 이후 대화에서 이전 정보를 다시 사용하는가? 원래 대화를 지우면 기억도 모두 지워진다는 생각
외부 연동 어떤 계정 권한으로 외부 자료를 읽고 행동하는가? 연동을 끊으면 이미 가져온 정보도 없어진다는 생각

ChatGPT·OpenAI에서 확인할 항목

개인 계정의 데이터 제어부터 확인합니다. 웹·모바일의 Settings → Data controls에서 현재 제공되는 데이터 사용·공유 설정을 확인합니다. 모델 개선 목적의 공유 선택지가 보인다면 회사의 기준에 맞게 설정하고 적용 상태를 기록합니다. 개인 계정에서 설정을 바꾸었다는 사실만으로 업무자료 입력이 허용되는 것은 아닙니다. 공식 데이터 제어 안내

업무용 워크스페이스와 데이터 조건을 확인합니다. Business·Enterprise·Edu 워크스페이스 데이터는 기본적으로 모델 학습에 사용되지 않습니다. 그렇다고 대화와 파일을 보관하지 않는다는 뜻은 아닙니다. 개인 계정의 데이터 설정을 기업용 계약과 같은 것으로 판단하지 말고, 회사가 승인한 작업 공간에서 사용하도록 안내합니다. 공식 기업용 보안 문서

기억과 연결 기능을 따로 검토합니다. ChatGPT의 Settings → Personalization에서 메모리를 관리합니다. 필요하지 않은 기억 기능은 끄고 기존 기억도 검토합니다. 기업 관리자는 앱·연결 관리에서 사용자를 제한하고, 지원되는 연결은 읽기 전용이나 승인된 동작만 허용합니다. 업무와 관계없는 개인 드라이브·메일함 연결은 해제합니다. 메모리 관리 · 기업용 앱·연결 통제

삭제 대상을 구분합니다. 특히 Work의 대화, Library 파일, 저장된 기억, 앱 연결과 브라우저 데이터는 별도 관리 대상입니다. 대화를 지웠다는 이유로 첨부파일이나 기억까지 모두 사라졌다고 판단하지 않습니다. Work 보관·삭제 범위

API는 별도 보관 정책을 읽어야 합니다. OpenAI API는 명시적 데이터 공유 동의가 없으면 기본적으로 모델 학습에 사용하지 않습니다. 그러나 기본 악용 모니터링 로그와 기능별 상태 저장은 별개입니다. 기본 로그는 최대 30일 보관될 수 있고 예외 조건도 있습니다. store:false만으로 모든 보관이 없어지는 것은 아니며, Zero Data Retention도 승인 여부와 기능·모델별 적용 범위를 확인해야 합니다. API 데이터 제어

Claude·Anthropic에서 확인할 항목

개인용은 모델 개선 설정을 확인합니다. Free·Pro·Max 등 개인용 계정에서는 Settings → Privacy → Help Improve our AI models를 확인하고 조직의 기준에 맞게 끕니다. 개인 유료 구독을 기업용 데이터 처리 조건으로 오해하지 않아야 합니다. 끄더라도 이미 완료된 학습을 소급 취소한다는 뜻은 아닙니다. 개인용 모델 개선 설정

기억과 연결을 정리합니다. 메모리는 현재 Settings → Memory, 일부 화면에서는 Settings → Capabilities에서 관리합니다. 원래 대화를 삭제해도 별도 기억이 남을 수 있으므로 기억 항목을 확인합니다. 외부 연결은 Customize → Connectors에서 관리하며, 불필요한 연결을 끊고 필요한 도구도 승인·차단 범위를 설정합니다. 메모리 안내 · 커넥터 안내

임시 대화도 보관 조건을 확인합니다. Claude의 Incognito 대화는 사용자의 대화 기록·메모리에 남지 않고 모델 학습에 사용되지 않지만, 기본 30일 보관과 기업 정책의 예외가 있습니다. Team·Enterprise에서는 조직 소유자의 데이터 내보내기에 포함됩니다. ‘임시’라는 이름을 민감정보 입력을 허용하는 근거로 삼지 않습니다. Incognito 공식 안내

기업용·API의 예외를 점검합니다. Team·Enterprise·API는 기본적으로 입력·출력을 모델 학습에 사용하지 않지만, 피드백 제출이나 명시적 동의의 조건을 별도로 확인합니다. API의 기본 삭제 주기, 파일 저장 기능, 법적·안전상 예외와 기업용 보관 설정도 다릅니다. 연결을 끊어도 이미 대화에 가져온 자료는 남을 수 있습니다. 상용 제품 학습 정책 · 조직 데이터 보관 · Google 연결 해제와 자료 보관

어느 제품이든 “학습하지 않습니다”라는 한 문장만으로 도입 검토를 끝내지 않는 것이 좋습니다. 특히 API·에이전트 기능은 모델, 도구, 파일 저장과 실행 환경이 추가될 때 처리 조건이 달라질 수 있습니다.

3. 계정과 API 키는 AI 밖에서도 지켜야 합니다

AI의 답변을 아무리 잘 통제해도 계정이 탈취되면 연결된 문서와 업무 도구가 위험해집니다. 회사가 관리하는 업무 계정과 개인 계정을 분리하고, 계정 공유를 금지하며, 이동·퇴사 시 계정과 연결 권한을 함께 회수해야 합니다.

다중요소 인증(MFA)을 지원하는 업무 계정에는 이를 적용합니다. Google·Microsoft 로그인이나 조직의 통합 로그인(SSO)을 사용한다면 실제 인증을 담당하는 서비스에서 MFA와 접근 정책을 강제합니다. 제품마다 자체 MFA 메뉴가 같다고 가정하지 말고, ‘SSO 설정 완료’와 ‘SSO 사용 강제’도 구분합니다. Claude SSO 설정과 강제 적용

API 키는 코드, 공유 문서, 프롬프트, 브라우저 코드와 앱 배포물에 하드코딩하지 않습니다. 비밀정보 관리 시스템에 저장하고 실행 시 안전하게 제공하며, 운영·개발 프로젝트와 서비스 계정을 분리합니다. 가능하면 지원되는 단기 자격증명을 사용하고, 키를 사용하는 경우 권한·유효기간·교체 정책과 폐기 절차를 정합니다. 환경변수를 쓰더라도 로그나 빌드 결과에 출력되면 노출될 수 있습니다. OpenAI 운영 권고 · Anthropic API 인증

유출이 의심되면 정기 교체일까지 기다리지 않고 키를 폐기·재발급하고 사용 기록을 확인합니다. 과도한 호출을 발견할 수 있도록 사용량 알림과 예산·호출 상한도 운영합니다. 경고만 보내는지, 실제 추가 호출을 차단하는지는 시험으로 확인해야 합니다.

4. 에이전틱 AI: 답변을 넘어 실제 업무를 수행할 때

에이전틱 AI는 목표를 받아 작업을 나누고, 도구를 호출하고, 결과를 확인해 다음 행동을 이어가는 시스템입니다. 모든 기능이 완전 자율일 필요는 없습니다. 사람이 중간에 승인하는 구조도 여기에 포함할 수 있습니다.

예를 들어 고객 문의를 읽어 담당 부서를 분류하는 업무는 비교적 좁게 시작할 수 있습니다. 이후 회신 초안을 만들고, 고객 기록을 수정하고, 실제 발송까지 맡기면 필요한 통제가 늘어납니다. 보안 운영에서도 로그 요약과 조치 제안, 실제 계정 잠금이나 시스템 격리는 서로 다른 단계로 다뤄야 합니다.

그림 1. 중요한 권한 판단은 모델 밖의 시스템에서 강제합니다. 승인 화면, 실행 API, 취소와 복구가 같은 작업을 가리켜야 합니다.

업무를 맡기기 전에는 목표, 허용 도구, 읽을 자료, 변경 가능한 대상, 비용·시간 상한, 승인 조건, 중단 방법을 정합니다. 읽기만 필요한 에이전트에게 삭제·발송 권한까지 줄 이유는 없습니다.

승인에는 실제 파일·수신자·금액·변경 전후 내용이 보여야 합니다. 모델이 “안전한 작업”이라고 설명하는 것만으로 승인하지 않도록 하고, 승인 뒤 대상이나 인자가 바뀌면 다시 검증하게 합니다. 외부 문서가 작업 목표를 바꾸려 하더라도 실행 API는 권한과 업무 규칙을 지켜야 합니다.

점검은 완료 보고와 실제 결과를 대조하는 방식으로 합니다. “메일을 보내지 않았다”는 답변이 나와도 발송 로그에 남아 있다면 통제가 실패한 것입니다. 시험 환경에서 권한 없는 요청, 잘못된 외부 지시, 도구 오류와 재시도를 넣어보고 실행 기록을 확인합니다. 정상 업무도 함께 시험해 과도한 차단을 발견합니다.

취소 버튼 역시 확인이 필요합니다. 화면 표시만 바뀌고 예약된 작업이나 다른 에이전트에 넘긴 작업이 계속 실행될 수 있습니다. 취소 시 신규 호출과 대기 작업을 막고, 실행 자격을 회수하며, 이미 반영한 변경은 정해진 복구 절차로 처리해야 합니다. 관련 위험은 OWASP Agentic Top 10 소개에서 항목별로 살펴볼 수 있습니다.

5. 거버넌스는 ‘사용 금지’ 공지보다 구체적이어야 합니다

직원이 어떤 도구를 써도 되는지, 민감한 업무는 어디에서 처리해야 하는지 모르면 편한 개인 서비스로 이동할 수 있습니다. 조직이 승인하지 않은 AI가 업무에 쓰이는 이른바 ‘섀도 AI’를 관리하려면, 현황을 파악하고 안전한 선택지를 제공해야 합니다.

정책에는 실제로 선택할 수 있는 기준을 적습니다

다음은 회사 상황에 맞게 조정할 수 있는 정책 문구의 예시입니다.

업무에는 승인된 서비스·요금제·계정만 사용한다. 미승인 서비스와 개인용 계정에는 개인정보, 민감정보, 영업비밀, 인증정보와 비공개 업무자료를 입력하지 않는다. 승인된 서비스에서도 허용 데이터 등급과 목적을 준수하고 필요한 최소 정보만 제공한다. 마스킹으로 위험이 충분히 낮아지지 않는 업무는 승인된 내부 환경이나 별도 검토 절차를 이용한다.

정책에는 허용 서비스 목록과 기능, 입력 가능한 정보의 등급, 외부 연동 승인, 생성 결과의 검토 책임, 기록 보관과 삭제, 예외 승인자를 포함합니다. 비밀번호·API 키처럼 AI 입력이 필요하지 않은 비밀정보는 별도로 명확히 금지합니다.

입력창의 경고 배너에는 “민감정보 금지”와 함께 승인된 대체 서비스와 문의 경로를 안내합니다. 위반 시에는 사실 확인·피해 제한·보고·재교육 등 처리 절차를 정하되, 실수로 정보를 넣은 직원이 신속하게 신고할 수 있도록 해야 합니다.

서비스별 담당자와 증거를 남깁니다

AI 하나마다 다음 내용을 한 장의 관리표로 정리하면 시작하기 쉽습니다.

서비스명·담당 부서 / 사용 목적 / 제품·요금제·공급자 / 데이터 등급 / 사용자·실행 계정 / 연결 도구 / 보관·삭제 조건 / 승인·중단 담당자 / 최근 점검일·다음 점검일

업무 부서는 사용 목적과 업무 영향을, 개발·운영은 구현과 운영 통제를, 보안·개인정보 담당은 위험과 처리 조건을 검토합니다. 남은 위험을 수용할 책임자도 정합니다. 보안담당자가 모든 업무의 허용 여부를 혼자 결정하는 구조는 지속하기 어렵습니다.

아래는 시스템별 자가진단에 사용할 수 있는 최소 점검표입니다. 각 항목에 적용 여부, 확인한 증거, 담당자, 미흡사항과 조치 기한을 함께 남깁니다. ‘해당 없음’에는 이유를 적고 ‘미확인’을 ‘양호’로 처리하지 않습니다.

점검 질문 확인할 증거의 예시
사용 목적·허용 서비스·담당자가 정해졌는가? 서비스 관리표, 승인 기록
어떤 정보가 외부로 나가고 어디에 남는지 아는가? 데이터 흐름도, 계약과 실제 설정
학습·보관·기억·연동을 각각 확인했는가? 해당 계정·기능의 설정과 삭제 시험
사용자·고객별 검색과 실행 권한이 유지되는가? 권한이 다른 시험 계정의 결과와 API 기록
외부 자료의 지시가 요청 밖 행동으로 이어지지 않는가? 시험 입력, 도구 호출, 실제 상태 변화
공급자·모델·도구·라이브러리의 변경을 관리하는가? 출처·버전 목록과 변경 승인
계정의 MFA와 계정·키의 최소 권한·회수 절차가 작동하는가? 인증 정책, 키 관리 내역, 회수 시험
중요한 실행은 정확한 내용으로 승인되고 중복되지 않는가? 승인 대상, 실행 인자, 거래 결과
비용·시간 상한과 취소·복구가 실제 작동하는가? 제한 시험, 중단 시점, 복구 결과
직원이 안전한 대체 수단과 신고 경로를 아는가? 안내·교육 기록, 신고와 후속 처리 사례

주기는 위험도와 변경 빈도에 맞게 정합니다. 예를 들어 사용 현황은 매월, 권한과 계약·보관 조건은 분기별로 검토할 수 있습니다. 이는 운영 예시이며 모든 기업에 정해진 의무 주기를 뜻하지 않습니다.

정기 점검 외에도 새 모델·공급자·데이터·외부 연결·쓰기 권한이 추가되면 관련 부분을 다시 검토합니다. 간단한 요약 도구에 메일 발송 기능 하나를 붙이는 변경도 보안상으로는 중요한 변경일 수 있습니다.

교육과 사고 대응도 실제 업무 장면으로 연습합니다

교육에서는 정책 문서를 읽는 데 그치지 않고, 메일에서 제거할 정보 찾기, 개인 공간과 업무 공간 구분하기, AI가 제시한 출처 확인하기, 의심스러운 승인 요청 거절하기를 짧게 연습할 수 있습니다. 보안팀이 승인된 프롬프트 예시와 더미 데이터를 제공하면 현업이 기준을 적용하기 쉬워집니다.

잘못된 자료 입력이나 비정상 실행이 발견되면 해당 연결·키·작업을 제한하고, 필요한 기록을 보호해 확보한 뒤 어떤 자료와 계정에 영향이 있었는지 확인합니다. 보안·개인정보·업무 담당자가 통지와 후속 조치 필요성을 판단하고, 삭제 요청·복구·권한 수정과 재점검으로 이어갑니다. 진단 로그 자체에 민감정보를 과도하게 남기지 않도록 수집 범위와 열람 권한도 정해야 합니다.

레드티밍은 이 운영 체계를 시험하는 방법 중 하나입니다. 승인된 범위와 가짜 데이터를 사용하고, 공격 문장 몇 개의 성공 여부보다 정보 접근·상태 변경·실행 결과를 증거로 남깁니다. KISA도 2026년 「AI 보안 레드티밍 가이드」를 공개했습니다. KISA 가이드

먼저 AI 서비스 하나의 정보와 권한을 그려봅니다

보안담당자가 모든 모델의 내부 구조부터 공부해야 하는 것은 아닙니다. 우선 현재 사용하는 AI 하나를 골라 누가 무엇을 입력하는지, 어떤 자료와 연결되는지, 무엇을 실행할 수 있는지, 누가 멈출 수 있는지를 확인해보면 좋겠습니다.

그다음 허용 기준을 정하고 실제 계정과 시험 데이터로 검증합니다. 사내 구축, 상용 서비스, 에이전트 모두 이 과정이 필요합니다. AI의 활용 범위를 넓힐수록 정보와 권한을 관리하는 범위도 함께 넓혀야 합니다.
