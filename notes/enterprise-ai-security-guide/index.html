AI 도입과 보안 설계 · 2편: 안전한 활용과 운영

이메일 초안을 쓰고, 보고서를 다듬고, 자료를 찾고, 코드를 만드는 일. 회사에서 AI를 활용하는 모습은 이제 특별하지 않습니다. 회의 내용을 자동으로 정리하거나, 고객 문의를 분류하고, 사내 문서를 검색하는 기능도 업무에 사용되고 있습니다.

보안담당자가 확인해야 할 대상도 함께 늘었습니다. 직원이 대화창에 붙여넣는 내용뿐 아니라, AI가 자동으로 읽는 문서와 연결된 계정, 생성한 코드, 대신 실행하는 업무까지 살펴봐야 합니다. 사람이 직접 입력하지 않은 정보도 AI 서비스로 전달될 수 있기 때문입니다.

어떤 AI를 도입할지, 어떤 정보를 허용할지, 운영 중 무엇을 점검할지를 보안담당자가 한 흐름으로 확인할 수 있도록 정리했습니다.

시리즈의 핵심

  • 구축 위치와 함께 데이터의 이동 경로, 사용자 권한, 실행 가능한 업무를 확인합니다.
  • 학습 제외, 대화 보관, 기억, 외부 연동은 서로 다른 설정입니다.
  • 허용 기준과 대체 수단을 제공하고, 정한 통제가 실제로 작동하는지 검증합니다.

1. 증가하는 AI 관련 보안사고

AI 활용이 확산되는 가운데, 공개적으로 보고되는 사고와 피해 사례도 늘고 있습니다. Stanford AI Index 2026의 공개 원자료에 따르면 AI 관련 사고·유해사례는 2023년 168건, 2024년 281건, 2025년 362건으로 집계됐습니다. 다만 여기에는 사이버 침해뿐 아니라 AI의 잘못된 판단 등으로 발생한 피해도 포함됩니다. 기업 대상 공격 건수보다는 AI가 현실에서 어떤 문제를 일으키고 있는지 보여주는 자료로 읽는 것이 적절합니다.

그림 1. 같은 공개 데이터 파일에 담긴 연도별 값을 사용했습니다. AI Incident Database 기반 자료이며, 실제 발생한 모든 사고나 기업의 사고 발생률을 뜻하지 않습니다.

보안담당자가 주목할 변화는 공격자가 AI를 활용하는 방식과 기업이 AI에 맡기는 업무가 함께 달라지고 있다는 점입니다. 2026년 6월 Five Eyes 사이버보안 기관 공동성명은 AI가 공격자의 진입 장벽을 낮추고, 공격의 속도와 복잡성을 높이고 있다고 경고했습니다. 취약점을 발견한 뒤 실제 공격에 이용하기까지 걸리는 시간이 짧아지면, 기업이 패치하고 대응할 여유도 줄어듭니다. Five Eyes 공동성명

기업 내부에서도 AI가 접근하는 정보와 권한이 늘어납니다. 이메일 초안을 작성하던 AI에 메일함 검색, 고객정보 조회, 실제 발송까지 맡기는 상황을 생각해볼 수 있습니다. 이때 보안 검토의 범위에는 답변의 정확성뿐 아니라 어떤 메일을 읽을 수 있는지, 누구에게 무엇을 보낼 수 있는지도 포함돼야 합니다. ENISA 역시 2026년 보고서에서 파일·인증정보·브라우저 세션 등에 접근하는 AI 애플리케이션과 주변 도구가 공격 대상이 되고 있다고 지적했습니다. 연결 기능이 늘어날수록 함께 보호해야 할 정보와 시스템도 많아지는 것입니다. ENISA Threat Landscape 2026

실제 침해 조사에서도 공격자의 AI 활용이 확인됩니다. 침해를 경험한 602개 조직을 조사한 IBM/Ponemon의 2026년 보고서에서는 조사 대상의 악의적 침해 중 약 25%에 AI가 활용됐으며, 해당 유형의 평균 침해 비용은 600만 달러로 나타났습니다. 딥페이크를 이용한 사칭과 AI를 활용한 악성코드 등이 대표적이었습니다. 특정 조사 표본의 결과이지만, 공격자의 AI 활용이 기업의 사고 대응과 비용 관리에서 고려해야 할 문제임을 보여줍니다. IBM 2026 공식 발표

피해는 시스템을 복구하는 것으로 끝나지 않을 수 있습니다. 고객정보가 노출되면 유출 경위를 설명하고 재발 방지 조치를 입증해야 합니다. AI가 잘못된 안내를 반복하거나 승인 없이 업무를 처리했다면 서비스에 대한 신뢰도 흔들릴 수 있습니다. 따라서 AI 보안 검토에서는 복구 비용과 함께 업무 중단, 고객 대응, 계약 관계와 평판에 미치는 영향까지 살펴봐야 합니다.

이런 변화에 대비하려면 우리 회사의 AI가 어떤 자료에 접근하고, 누구의 권한으로, 어디까지 실행할 수 있는지부터 파악해야 합니다. 같은 모델을 사용하더라도 사내 문서만 검색하는 AI와 고객 요청을 받아 내부 시스템을 변경하는 AI에는 서로 다른 통제가 필요합니다. 다음에서는 기업의 AI 도입 방식을 네 가지 구조로 나누어, 각각 어디에 보안의 초점을 맞춰야 하는지 살펴보겠습니다.

2. 기업의 AI 도입 방식, 네 가지 구조로 살펴봅니다

국정원의 「국가·공공기관 AI보안 가이드북」은 내부망 전용, 내부망용 AI의 외부망 연계, 대민서비스용 AI의 내부망 연계, 상용 AI서비스 활용을 구분해 다룹니다. 국정원 AI보안 자료 · 국회도서관의 가이드북 목차

그림 2. 주요 요청 경로와 신뢰 경계를 단순화한 그림입니다. 실제 구성에서는 인증, 통신 통제, 응답 경로와 운영 로그를 더해 확인해야 합니다.

표는 좌우로 움직여 볼 수 있습니다.

도입 유형 장점 부담과 주의점 먼저 검토할 만한 상황
사내망 전용 구축 데이터 이동과 운영 환경을 직접 통제하기 좋음 연산 자원·운영 인력·업데이트 비용, 내부 권한과 공급망 관리 필요 외부 처리가 제한되는 데이터가 있고, 자체 운영 역량을 확보한 조직
사내 AI의 외부망 연계 사내 자료와 최신 외부 정보·기능을 함께 활용 외부 자료의 악성 지시, 외부 전송 경로와 연결 도구 관리 필요 내부 지식과 외부 웹·API를 결합해야 하는 조사·개발 업무
고객서비스 AI의 사내망 연계 고객 문의와 내부 업무 데이터를 연결해 서비스 제공 외부 사용자의 입력이 내부 시스템에 닿음. 고객별 격리와 거래 권한이 중요 주문·예약·계약 조회처럼 인증된 고객에게 내부 정보를 제공하는 서비스
상용 AI 구독·API 활용 초기 도입이 빠르고 모델·인프라 운영 부담이 작음 공급자의 계약·보관·연동 정책, 비용과 변경사항에 의존 일반 문서 업무나 빠른 검증, 승인된 클라우드 처리가 가능한 업무

이 유형은 완전히 배타적인 분류가 아닙니다. 사내 업무 앱에서 상용 모델 API를 호출하거나, 고객서비스의 일부만 사내 모델로 처리할 수도 있습니다. 회사 규모보다 데이터의 민감도, 외부 처리 허용 여부, 필요한 연결, 운영 역량, 비용을 기준으로 선택하는 편이 좋습니다.

예를 들어 일반 안내문 작성이 목적이라면 승인된 기업용 상용 서비스를 먼저 검토할 수 있습니다. 외부 반출이 어려운 핵심 기술문서를 분석해야 한다면 자체 구축이나 승인된 격리 환경을 검토할 수 있습니다. 이때도 통제 수준이 요구사항을 만족하는지 확인해야 하며, ‘대기업은 사내 구축, 중소기업은 상용 서비스’처럼 나눌 수는 없습니다.

3. AI 수명주기: 도입부터 운영을 끝낼 때까지

AI 보안 검토는 오픈 직전 한 번의 진단으로 끝나지 않습니다. NCSC의 지침을 따라 설계 → 개발 → 배포 → 운영·유지보수의 네 단계로 보면 책임과 점검 시점을 정리하기 쉽습니다. 이는 수명주기를 설명하는 한 가지 틀이며, 모든 지침이 같은 단계 수를 사용하는 것은 아닙니다. NCSC 안전한 AI 시스템 개발 지침

표는 좌우로 움직여 볼 수 있습니다.

단계 주요 위협과 실수 보안담당자가 확인할 결과물
설계 목적에 비해 과도한 데이터·권한, 책임과 허용 범위의 누락 업무 목적, 데이터 흐름도, 데이터 등급, 위협 시나리오, 책임자
개발 오염된 데이터·모델, 취약한 라이브러리, 코드·설정의 비밀키 데이터 출처와 반영 기록, 구성요소 목록, 코드·비밀정보 검사 결과
배포 인증·인가 누락, 공개된 관리 화면, 시험용 권한의 운영 반영 운영 권한표, 망·저장 설정, 승인·차단 시험, 복구·중단 절차
운영·유지보수 모델·문서·도구 변경에 따른 통제 약화, 기억 오염, 비용 폭증 변경 전후 평가, 실행 기록, 이상 탐지, 권한 재검토, 사고 대응 훈련

상용 AI를 쓰는 기업도 이 과정에서 빠지지 않습니다. 모델 학습은 공급자가 맡더라도 서비스 선정, 계정 설정, 연결 권한, 입력 자료, 생성 결과를 사용하는 책임은 남습니다.

운영 종료도 포함해야 합니다. 서비스를 해지할 때는 계정과 API 키, 외부 연동을 회수하고 대화·첨부파일·기억·검색 색인·백업의 처리 기준을 확인합니다. 서비스 화면에서 삭제되었는지와 공급자 시스템에서 어떤 일정으로 삭제되는지는 별개의 확인 항목입니다.

4. 도입 유형에 따라 중점 보안 설계가 달라집니다

사내망 전용: 내부정보도 사람마다 읽을 자격이 다릅니다

외부 인터넷과 단절되어 있어도 모든 직원이 모든 정보를 읽어도 되는 것은 아닙니다. 일반 직원에게 임원 인사자료가 검색된다면, 정보가 사내에 머물렀더라도 권한 통제에 실패한 것입니다.

특히 모델 학습과 문서 검색의 권한 관리를 구분해야 합니다. 공통 모델에 학습시킨 내용을 나중에 사용자별로 정확히 꺼내지 못하게 만드는 일은 문서 접근 권한을 적용하는 것과 다릅니다. “이 자료는 관리자용”이라고 모델에 지시하는 것만으로 인가를 보장할 수 없습니다.

민감도가 다른 데이터를 하나의 모델에 학습시킬 필요가 있는지 먼저 검토합니다. 사내 자료를 검색해 답변에 활용하는 RAG를 쓴다면, 검색 단계에서 원본 문서의 사용자·조직별 권한을 적용하고 삭제·권한 회수도 색인과 캐시에 반영해야 합니다. 필요한 경우 데이터와 서비스 경계를 분리합니다.

점검 예시: 권한이 다른 두 계정으로 같은 문서를 질의합니다. 답변에서 가렸는지만 보지 말고 검색된 문서와 모델에 전달된 내용도 확인합니다. 모델·라이브러리 반입, 이동식 매체, 업데이트, 원격 유지보수와 외부 통신 설정도 함께 점검합니다. 격리된 운영 환경에도 공급망은 존재합니다.

사내 AI의 외부망 연계: 들어오는 자료와 나가는 정보를 함께 봅니다

외부 웹페이지나 메일에는 사람이 읽을 정보와 AI의 행동을 바꾸려는 지시가 함께 들어올 수 있습니다. 외부 자료를 읽게 했을 뿐인데 사내 자료를 전송하도록 유도된다면 프롬프트 인젝션과 연결 권한의 문제가 이어진 것입니다.

외부 접속 목적지와 프로토콜을 정하고, 필요한 경로로만 통신하게 합니다. 연결할 도구·플러그인·MCP 서버의 출처와 권한을 승인하며, 쓰기·발송 기능은 읽기 기능과 구분합니다. MCP는 AI와 도구를 연결하는 방식이지 도구의 안전을 보증하는 표시가 아닙니다.

점검 예시: 테스트용 웹 문서에 업무와 관계없는 무해한 지시를 넣고, 원래 요청 밖의 검색·전송이 일어나는지 확인합니다. 외부 전송 차단을 시험할 때는 화면의 거절 문구뿐 아니라 프록시·도구 호출·수신 측 기록을 대조합니다. 허용 도메인으로 보냈더라도 허용되지 않은 파일을 전송했다면 문제가 남습니다.

고객서비스 AI의 사내망 연계: 내부 시스템 앞에 별도의 권한 검사가 필요합니다

고객용 챗봇이 내부 데이터베이스에 넓은 권한으로 직접 접근하게 만들면 외부 입력의 영향이 커집니다. 고객서비스 계층과 내부 업무 사이에 필요한 기능만 제공하는 API를 두고, 실제 요청자의 신원과 고객·조직 범위를 서버에서 검사해야 합니다.

모델이 전달한 고객번호를 그대로 신뢰해서는 안 됩니다. 로그인한 고객에게 해당 주문을 조회하거나 변경할 권한이 있는지 업무 API가 다시 판단해야 합니다. 조회와 변경은 권한을 분리하고, 취소·환불처럼 중요한 거래에는 추가 확인과 중복 실행 방지 기준을 둡니다.

점검 예시: 고객 A의 시험 계정으로 고객 B의 주문번호를 질문하거나 도구 인자에 넣어봅니다. 다른 고객의 정보가 답변·첨부파일·세션 기억에 나타나지 않는지 확인합니다. 인증·인가, 입력 검증, 호출 제한, 세션 격리 같은 기존 애플리케이션 보안은 AI를 도입해도 그대로 필요합니다.

상용 AI 활용: ‘유료’보다 계약과 사용 범위가 중요합니다

개인이 결제한 유료 AI 계정과 회사가 관리하는 기업용 워크스페이스는 관리·데이터 처리 조건이 다를 수 있습니다. 서비스 이름만 승인할 것이 아니라 제품·요금제·계정·기능·허용 데이터 종류까지 정해야 합니다.

검토하지 않은 개인용·상용 AI에 개인정보, 민감정보, 영업비밀, 내부 소스코드와 인증정보를 입력하지 않는 것을 기본으로 두는 편이 안전합니다. 승인된 기업용 서비스나 API에서도 모든 자료를 무조건 허용할 수는 없습니다. 업무 필요성, 처리 근거, 계약, 보관과 삭제, 국외 처리 여부, 하위 처리자, 관리자 접근, 사고 통지와 반출 조건을 확인해 허용 범위를 정합니다.

점검 예시: 조직이 승인한 워크스페이스에서 작업 중인지, 개인 공간으로 쉽게 전환해 자료를 올릴 수 있는지, 허가하지 않은 클라우드 드라이브 연결이 가능한지 확인합니다. 데이터 유출 방지 도구(DLP)나 업로드 경고는 보조 통제이며, 예외 승인과 점검 기록을 함께 운영해야 합니다.

이 네 유형의 세부 위협은 OWASP LLM Top 10 소개와 연결해 점검할 수 있습니다. 목록의 번호를 확인하는 데서 멈추지 말고, 우리 서비스에서 누가 어떤 정보를 읽고 어디까지 실행할 수 있는지로 바꿔 질문해야 합니다.
